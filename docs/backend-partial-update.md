# Раздел 1.2: обнуление полей через PUT

> **Статус: реализовано.** Пять пунктов чеклиста закрыты, 83 теста зелёные, живая проверка
> проведена на всех семействах маршрутов. Схлопывание каталожных контроллеров в общий базовый
> класс сюда **не** вошло — обоснование в конце.

Продолжение части 3 `docs/backend-concepts.md` и раздела 1.2 `TODO.md`. Там выбран вариант D
(`presentFields` + рефлексия) и описан конвейер; здесь — что из этого получилось, чем реализация
отличается от плана и почему, и что вскрылось по дороге.

---

## Что было сломано

После `be4f97f` мапперы работают с `NullValuePropertyMappingStrategy.IGNORE`. Это правильно для
отсутствующего поля и неправильно для явного `null`: после десериализации в POJO они неразличимы.
`UpdatePolicyValidator` при этом уже спрашивал, кому можно обнулять поле, — и ответ выбрасывался.
Весь слой полевых прав был проверкой разрешения на операцию, которой приложение не умело.

Плюс структурная половинчатость: сырой JSON видели 11 контроллеров, а девять наследников
`AbstractCrudController` принимали типизированный DTO. Даже добившись обнуления в первых,
получили бы `/api/components/{id}` умеет, а `/api/devices/switches/{id}` для того же объекта —
нет.

## Что построено

Четыре новых класса; всё остальное — перевод существующих на них.

| класс | пакет | зачем |
|---|---|---|
| `JsonPayload` | `web.payload` | чтение тела как дерева: `asObject` / `presentFields` / `bind`. Это тот самый `extractPresentFields`, скопированный по файлам **восемь раз** |
| `PartialUpdate<T>` | `web.payload` | связанный DTO + какие поля пришли + политика вызывающего. Едет из контроллера в сервис |
| `PartialUpdateReader` | `web.payload` | один вызов вместо пяти шагов в каждом PUT-обработчике |
| `NullFieldApplier` + `EntityNullability` | `security.policy` | применяет явные `null` и решает, можно ли |

Конвейер, теперь одинаковый на **всех** маршрутах:

```
raw JSON → ObjectNode → presentFields → bind (дискриминатор пиннится) → PartialUpdate
  → mapper.updateFromTo   (IGNORE: только non-null)
  → applyReferences       (только non-null id)
  → update.applyNulls     (явные null: политика + возможность)
  → save + mapToDto в той же транзакции
```

## Три отличия от плана, каждое — следствие найденного

### 1. Решение о праве обнулить принимается не при чтении тела, а при применении

План: прочитать тело → `UpdatePolicyValidator.validate(...)` → применить. Так и было сделано
сначала, и живая проверка это сломала: **фронтенд сохраняет объект целиком** —
`{...item.value, ...editForm.value}` в `GenericDetailView.vue:592` — то есть отправляет обратно
всё, что вернул GET, включая `null` в каждом незаполненном поле. А `description` в `NamedTo`
помечен `ADMIN_NULLABLE`. Значит любое сохранение под USER записи с пустым описанием отвечало бы
403 — ради защиты значения, которое и так `null`.

Правило, которое из этого следует: **политика управляет изменением, а не повторением.** Является
ли `null` изменением, видно только против сохранённого значения, то есть внутри транзакции. Поэтому
`NullFieldApplier` сначала отбирает поля, которые действительно что-то поменяют, и только их
предъявляет валидатору. `PartialUpdateReader` теперь резолвит политику, а не проверяет.

Проверено обеими сторонами: `NullFieldApplierTest` — `null` поверх пустого не требует прав, тот же
`null` поверх заполненного под USER даёт 403; `NullificationEndpointTest` — объект целиком,
отправленный обратно как есть, принимается под USER.

### 2. Второй рубеж — на сущности, а не на DTO

Уровень доступа берётся из аннотаций **DTO**, и по умолчанию поле без аннотации —
`ADMIN_NULLABLE`. Этого недостаточно, чтобы обнулять: `ComponentTo.manufacturer` объявлен
`ADMIN_NULLABLE` над колонкой NOT NULL, а `LocationTo`, `InstallationTo` и `PortTo` не имели
аннотаций вовсе. Запись такого `null` — constraint violation, то есть **500 на запрос, который
API только что принял**.

`EntityNullability` читает JPA-разметку и отвечает, может ли свойство физически быть `null`:
примитив, `@Column(nullable = false)`, `@JoinColumn(nullable = false)`, `@Basic(optional = false)`,
идентификатор, управляемая коллекция. Отказ — **422**, а не 403: это не про того, кто спрашивает,
а про то, что невозможно. Разные коды намеренно: «вам нельзя» и «так нельзя никому» — разные
ответы.

Коллекция отказывается отдельным пунктом: Hibernate следит за загруженной коллекцией через свою
обёртку, и подмена её на `null` выбрасывает вместе с обёрткой состояние ассоциации.

### 3. Обнуление FK делает апплаер, а не резолвер

План отдавал `componentNatureId: null` резолверу. Сделано наоборот: DTO везёт `<имя>Id`, сущность
хранит `<имя>`, так что обнуление ассоциации — та же операция с отброшенным суффиксом. Резолвер
трогает id только когда он присутствует **и** не `null`, поэтому половины не пересекаются, а
сигнатуры шести методов резолвера и десятки их вызовов остались нетронутыми. Один набор сторожей
вместо одного на метод.

## Разметка полей, которой не было

`LocationTo`, `InstallationTo`, `PortTo`, `EthernetPortTo`, `FiberPortTo` не несли ни одной
`@FieldAccess` — 118 полей по умолчанию считались `ADMIN_NULLABLE`. Пока никто не обнулял, это
ничего не значило; с работающим обнулением это значило бы «USER не может сохранить локацию».

Разметка проставлена по правилу, уже принятому в `ComponentTo`, а не придумана заново:

| условие в DTO | уровень |
|---|---|
| `@Schema(accessMode = READ_ONLY)` — производное поле | `READ_ONLY` |
| `@NotNull` / `@NotBlank`, либо колонка NOT NULL / примитив | `REQUIRED` |
| остальное | `USER_WRITABLE` |

Итого: Location 3/22/12, Installation 5/28/9, Port 2/20/31, EthernetPort 0/3/4, FiberPort 0/5/7
(REQUIRED / READ_ONLY / USER_WRITABLE). Это снимок намерения, а не новая политика: поменять
уровень — одна аннотация.

## Третье отличие, которого не было в плане вовсе: «отсутствует» пришлось восстанавливать

Стратегия `NullValuePropertyMappingStrategy.IGNORE` задаёт мапперу ровно один вопрос: свойство
`null`? DTO с инициализатором поля отвечает на него неверно. `AccessPointTo.ssids` объявлен
`= new HashSet<>()`, поэтому тело, не упоминающее `ssids`, всё равно доезжает до маппера с пустым
множеством — и сгенерированный `updateFromTo` честно чистит сохранённые SSID и добавляет обратно
ничего.

**Это измерено, а не выведено:** `PUT /api/devices/access-points/{id}` с телом
`{"description": "probe"}` стёр три SSID. До этой работы такой запрос был недостижим — частичный
PUT на этих девяти маршрутах отвечал 500, — так что дефект не «был и остался», а открылся вместе
с маршрутом.

Инициализаторов таких 126: каждый `= new ArrayList<>()` и каждый `Boolean flag = false`. Снимать
их нельзя — другой код читает их как обещание, что коллекция не `null`. Поэтому
`JsonPayload.blankAbsentProperties` возвращает DTO в то состояние, которое должно было получиться
при связывании: **чего в теле не было, того нет и в DTO**. Примитивы не трогаются — им нечем
сказать «отсутствует», ровно поэтому слой полевых прав и считает колонку за примитивом
необнуляемой.

Порядок в `PartialUpdateReader` из-за этого стал важен: дискриминатор пиннится **до** снятия
списка полей, иначе следующая же строка вычистила бы его обратно.

Закреплено `JsonPayloadTest`: коллекция, не упомянутая в теле, переживает настоящий маппер;
явный `[]` по-прежнему очищает — это просьба, а не умолчание.

## Два дефекта, найденные живой проверкой; оба были до этой работы

Оба подтверждены прогоном **предыдущего** кода, а не выведены из чтения.

Заодно поправлены `EthernetPortMapper` / `FiberPortMapper`: `specifications` там — тоже
вычисляемая карта, и маппер генерировал `clear()/putAll()` поверх временного `HashMap`. Сегодня
это безвредно ровно потому, что карта изменяемая, — то есть той же формой, что положила установки.

1. **`PUT /api/installations/{id}` отвечал 500 на любое тело, включая `{}`.**
   `Installation.getOccupiedRackPositions()` — вычисляемый геттер, возвращающий `List.of()`, когда
   установка не в стойке. MapStruct увидел геттер коллекции, счёл его целью и сгенерировал
   `entity.getOccupiedRackPositions().clear()`. Лечится одной `@Mapping(ignore = true)` на
   `updateFromTo` и `toEntity`; закреплено `InstallationMapperTest`.

2. **Частичный PUT на девяти маршрутах `AbstractCrudController` отвечал 500
   (`InvalidTypeIdException`).** `RackTo` наследует `@JsonTypeInfo` от `ComponentTo`, поэтому
   Jackson требует `componentClass`, даже когда целевой тип уже назван. То есть обнуление на этих
   маршрутах было невозможно не только из-за типизированного `@RequestBody`. Три полиморфных
   контроллера обходили это вручную для своей иерархии; теперь пиннинг живёт в `JsonPayload.bind`
   и берёт значение из целевого типа. Значение **перезаписывается**, а не подставляется по
   умолчанию: тип определяет маршрут, и телом его не сменить. Закреплено `JsonPayloadTest`.

  локальную пару DTO/сущность для веток, которых нет в модели), `NullificationEndpointTest` (4 —

  выбирает `UpdatePolicyResolver` по принципалу `AuthUser`, а мок-принципал им не является),
  `JsonPayloadTest` (8), `InstallationMapperTest` (2).
- **Права не сдвинулись:** `generate_permission_seed.py --check` — те же 81; отчёт реестра на
  старте — `109 эндпоинтов, 101 под правом, 0 без аннотации, 0 непроксируемых, 0 отсутствующих`.
  Это не формальность: смена сигнатуры `AbstractCrudController.update` меняет `Method`, по
  которому реестр ключует права.
- **Живьём** (профиль `local`, порт 8090): сохранение объекта целиком под USER — 200 на всех
  десяти семействах маршрутов; частичный `{"description": null}` под ADMIN — 200 и поле пусто;
  под USER — 403; `{"manufacturer": null}` — 422 с текстом `column manufacturer is NOT NULL`;
  попытка сменить тип телом — проигнорирована; частичный PUT точки доступа не трогает её SSID,
  а `{"ssids": []}` их очищает.
- **Отказ откатывает весь запрос:** под USER `{"name": "CHANGED", "description": null}` — 403, и
  `name` остался прежним. Проверка политики теперь идёт внутри транзакции, после маппера, поэтому
  это не самоочевидно и проверено отдельно.

## Чего здесь нет и почему

**Схлопывание семи каталожных контроллеров в общий базовый класс.** `TODO.md` предлагал делать это
вместе с 1.2, и обоснование было верным ровно наполовину: копия `extractPresentFields` в восьми
файлах — это то, что переписывает 1.2, и трогать её дважды не хотелось. Эта половина закрыта —
восемь копий удалены, файлы похудели.

Вторая половина — сведение четырёх контрактов сервисов (`DtoCrudService` возвращает `T`,
`UpdatableCrudService` возвращает `E` из одноимённого метода, плюс два самодельных) — к 1.2
отношения не имеет и стоит миграции сигнатур примерно по двадцати сервисам. Сложенная в один
коммит с изменением поведения, она сделала бы диф непроверяемым. Осталась отдельным пунктом; вся
подготовка к ней теперь есть: PUT-обработчики стали одинаковыми с точностью до имени типа.
